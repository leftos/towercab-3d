TC3D-218: where a building part's storeys come from

OSM Buildings facades, feat/osm-facades at ca4d7fc. Headless Edge, 1596×800 canvas, 12:00 local, building quality high, tileset SSE 4. Each view is shot three times in one page session; only storeysAndWall in buildingStyle.ts changes between lanes.

The question. storeysAndWall (buildingStyle.ts:221-236) treats a feature as a building part when its part#building:levels or part#height parses. Everything else (the ground lookup, the probe) uses isBuildingPart (:187-190, true when part#elementId is present). Should the storey rule switch to isBuildingPart, and if so, where should a part without its own tags get its numbers?

  • A, today: a feature with its own part# levels or height reads only those; any other feature, a part without its own tags included, reads the unprefixed tags (for a part, those are its parent's) and falls back to cesium#estimatedHeight.
  • B, strict switch: isPart = isBuildingPart(feature); a part reads only its own part# levels and height. A part with neither gets storeys 0 and wall NaN: the grammar's default storey.
  • C, switch with parent fallback: isPart = isBuildingPart(feature); a part reads its own part# value for each of levels and height when present, else the parent's unprefixed value for that one tag.

The shader only uses the two numbers together: the storey height is wall ÷ storeys, clamped to 2.4–6 m, and only when storeys ≥ 1 and the wall is under 53 m; otherwise the grammar's default storey is drawn. So most differences in the numbers draw nothing different.

Read. B. It draws differently from today on 2 of 960 loaded parts across the Bay Area, and where it does (Aluxor SFO below), its rows match the part's 3-storey siblings while A's 5 m rows come from the parent's tags. C changes 40 parts, and each change mixes a part's own height with the parent's storey count (Terminal 2: the whole building's 4 levels spread over 25–40 m parts, all clamped to 6 m rows; one part gets 2.4 m rows over its 7.4 m wall). Read per tag, the parent's numbers describe a different volume from the part.

Read as a whole-group fallback (use the parent's tags only when the part has neither of its own), C is exactly A: no loaded feature without part#elementId carries a part# level or height (0 of 13,924), so the two tests always agree.
