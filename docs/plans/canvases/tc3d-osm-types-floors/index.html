OSM building types and floor lines: decision mocks

Open decisions of TC3D-218 (type OSM building parts from their outline, then by shape near the field) and TC3D-220 (facade floor lines don't start at the building's ground), numbered as in the code map. Every still is the real app (feat/osm-facades at 4b888e2) in headless Edge with the facade shader, noon fixed time, building quality high, u_fade 0. The lanes other than "today" are a throwaway prototype in a scratch worktree: a per-tile lookup texture, filled from each tile's vertex buffers, feeds the shader each building's base, roof, footprint and a debug class. TC3D-220 decision 1: where a building's floor lines start

Today the shader measures height from the tile's model origin (facadeShader.ts:477), so each building's storey grid starts at a random height. (a) keeps that on the ion tiles and fixes floors only in the generated near-field buildings of TC3D-168, so on ion tiles (a) looks exactly like today. Lane (c) needs the same per-building data as (b): the shader knows neither where the roof nor where the ground is in the tile's frame, and the packed wall height is a length, not a position.

TC3D-220 decision 2: how each building's base reaches the shader

All four style-colour channels are in use. Shrinking the hash or coarsening storeys each frees one bit, so together they carry a base phase of 4 states: 0.75 m steps at a 3 m storey. The phase must still be computed per tile from the same vertex readback, because the shader's height origin is per tile (TC3D-220 probe). Counts below are over the 6,091 elements loaded around the San Bruno pose.

TC3D-218 decision 5: shape fallback thresholds and the "inside an airport" test

Top-down, 6,500 m, building LOD forced fine (SSE 2) so every building draws. Footprint is the up-facing triangle area read back from each tile (the same readback as the lookup texture, no extra GPU cost). Untagged buildings carry cesium#estimatedHeight 3 m, so "low" passes for almost every untyped building and area is the only real test; "4-8 levels" fires only where levels or height are tagged (5 buildings at most per airport). Numbered markers are the named buildings the fallback types; unnamed ones cannot be judged from tags.

TC3D-218 decision 7: the KSFO "central garage" (settled, no lanes)

OSM relation 15730419 is the International Terminal Main Hall: its outline member, relation 14273628, is named "International Terminal Main Hall" (aeroway=terminal, building=transportation, 5 levels, 40 m). The curved garage below the tower is relation 2920181 "Domestic Garage" (amenity=parking, parking=multi-storey), which the branch already classes GARAGE. Inheriting TERMINAL onto 15730419's 12 parts is therefore right. docs/plans/canvases/osm-facades/README.md:11 misnames the garage as relation 15730419. Tower eye, heading 274, pitch −7, FOV 45; the main hall's parts are drawn as TERMINAL (prototype class override).

Recommendations

Decision 1: (b) floors from each building's ground. It is the only lane where ground-floor windows line up along a street and at the ramp. Worst case: a partial storey under the roof (a thin window row at KOAK, a blank band in San Bruno).

Decision 2: the per-tile lookup texture. No look change. The colour-bit options cost palette variety or storeys and buy only a 0.75 m phase, yet need the same readback. Worst case: about 4 ms per loaded tile (22 ms for the slowest), and private Cesium API to re-check on each upgrade. Check the 228 floor first.

Decision 3: lines from the building's ground. Stacked parts keep one rhythm. Worst case: a cut row at a raised part's bottom edge.

Decision 5: the aerodrome polygon with set B (≥ 1,500 m², ≤ 20 m). The radius test types whole industrial districts (98 hangars at KOAK). Worst case: a fire station inside the fence gets hangar walls. Drop the "4-8 levels" rule or make it tag-only: untagged buildings never reach it.

Decision 7: no longer a question; fix the osm-facades README row.
